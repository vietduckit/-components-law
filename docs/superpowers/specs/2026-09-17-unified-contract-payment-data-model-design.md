# Unified Contract Payment Data Model — Contract Payment Schedule Collection + By Service Task-Trigger — Design Spec

Date: 2026-09-17

Status: Schema already built by the user directly in the Admin UI (confirmed via screenshots, see §4). This spec documents the as-built schema, fills the remaining gaps needed to implement the automation logic, and supersedes `2026-09-15-by-case-payment-request-automation-design.md` §4's `paymentSchedule.installments[]` JSON approach for By Case.

## 1. Overview

By Case's installment schedule currently lives as a JSON array inside `contracts.paymentSchedule` (`{installments: [...]}`), read/written by 3 separate JS Blocks that each parse/rebuild that structure by hand (`ContractCreateForm.js`, `ContractDetailView.js`, `ContractPaymentScheduleDetailBlock.js`). This works but doesn't extend cleanly: there's no real FK from a `paymentRequests` row back to "which installment created me" (today it's an implicit match on `installmentNo`), no referential integrity, and no way to reuse the same shape for By Service (whose billing unit isn't an installment schedule at all — it's per-service, driven by task completion, per the By Service business flow agreed on 2026-09-16/17).

This spec replaces the JSONB approach with a real collection, `contractPaymentSchedule` (one row per installment, proper FK to `contracts` and to the `paymentRequests` it generates), and adds a lightweight task-trigger mechanism for By Service that needs no new collection at all — it reuses `contractServices`/`projectServices` (already the natural billing unit) plus one new boolean on `tasks`.

Together with the existing `contractBillingPlans` collection (Retainer, shipped 2026-09-08), all 3 contract types now follow the same shape: `contracts` holds common fields, each type's own billing unit lives in its own collection or reuses an existing one, and `paymentRequests` gets a nullable FK back to whichever billing unit produced it.

## 2. Goals

- By Case's installment schedule is a real, queryable collection with FK integrity to both `contracts` and `paymentRequests` — no more JSON parsing to answer "which installments does this contract have" or "which Payment Request came from which installment."
- By Service gets task-completion-triggered Payment Request creation, matching the business flow already agreed: 1 service = 1 Payment Request, created (not merely activated) once every task the lawyer flagged as a payment trigger for that service reaches `done`.
- The existing By Case activation rules (condition met AND due date, in either order) carry over unchanged and are reused as-is for By Service's own activation.
- No auto-creation of a real Payment or Invoice — unchanged from the existing convention; an active Payment Request is still a queue item for a human.

## 3. Non-goals

- **Migrating existing contracts' `paymentSchedule` JSON into `contractPaymentSchedule` rows is a separate, explicit follow-up task**, not bundled into this spec's implementation — see §7. This spec's triggers only act on new rows created from this point forward; nothing in this spec back-fills history.
- **Not changing `contractBillingPlans` (Retainer)** — already correct, untouched.
- **Not adding a By Service child collection.** `contractServices` / `projectServices` already are the billing unit; adding another collection on top would duplicate data that already exists (violates this project's own "don't design for hypothetical future" convention already applied elsewhere this session).
- **Not auto-creating Payment/Invoice records** — same convention as the By Case spec's §3.
- **Not changing `dueDate`/`conditionMet`/`status` on `paymentRequests`** — they keep doing exactly what they already do; the new FKs (§4) only add "where did this PR come from," not new state.

## 4. Schema — as already built (confirmed via Admin UI screenshots, 2026-09-17)

### New collection: `contractPaymentSchedule` ("Contract Payment Schedule")

| Field display name | Field name | Type | Notes |
|---|---|---|---|
| ID | `id` | snowflakeId | title field |
| contractId | `contractId` | bigInt | raw FK column |
| Contracts | `contracts` | belongsTo → contracts | many-to-one; despite the plural display name this is a single parent contract |
| Installment No | `installmentNo` | bigInt | order within the contract |
| Label | `label` | string | e.g. "Đợt 1 - Ký hợp đồng" |

| Amount | `amount` | float | resolved amount in contract currency |
| Trigger Type | `triggerType` | string, single select | should carry the same 3 options as `paymentRequests.triggerType` — **confirm the option list matches `on_signed`/`on_task_done`/`on_case_done` exactly** before wiring the trigger (same caveat the 2026-09-15 spec raised for `paymentRequests.triggerType`) |
| Due Date | `dueDate` | date/datetime | Added after this spec's first draft (see §6 revision) — a **one-way seed value** copied onto the generated `paymentRequests.dueDate` at creation time only, not a synced field |

Before writing the SQL trigger file, confirm the real table name (almost certainly `contractPaymentSchedule` or `contractPaymentSchedules` — this project's other collections are plural, e.g. `contracts`, `tasks`, `paymentRequests`) via `information_schema.tables` or the collection's own settings panel.

### `paymentRequests` — new fields added

| Field display name | Field name | Type | Used by |
|---|---|---|---|
| Source Snapshot | `sourceSnapshot` | json | **Purpose to confirm with user** — presumed to be a point-in-time snapshot of whichever record generated this PR (the schedule row's label/percentage/amount, or the service's totalAmount/comboName), so financial reporting stays accurate even if the source row is later edited — same audit-trail role `pricingSnapshot` already plays for combo-priced `projectServices` rows. Not yet populated by any trigger — this spec proposes what writes it (§5). |
| Installment No | `installmentNo` | bigInt | By Case — denormalized copy of `contractPaymentSchedule.installmentNo`, kept directly on the PR so existing frontend code (`ContractPaymentScheduleDetailBlock.js`'s `summarizePaymentRequestsByInstallment`, keyed by `installmentNo`) keeps working without a join |
| Contract Payment Schedule | `contractPaymentSchedule` | belongsTo → contractPaymentSchedule | By Case — which installment produced this PR |
| Case Services | `projectServices` | belongsTo → projectServices | By Service — which case-level service line produced this PR |

`dueDate`, `conditionMet`, `status`, `triggerType` (already existing on `paymentRequests`) are unchanged — they remain the single source of truth for a PR's own activation state; `contractPaymentSchedule` stays a purely static definition (no dueDate/conditionMet duplicated there), avoiding a two-places-to-update bug.

### `tasks` — new field added

| Field display name | Field name | Type | Notes |
|---|---|---|---|
| isPaymentTrigger | `isPaymentTrigger` | boolean (checkbox) | lawyer ticks this on any task, in any case, that should count toward that task's service's payment trigger |

Already-existing relevant fields on `tasks` (unchanged, just noted for §5): `linkedPaymentRequestId` (belongsTo → paymentRequests, By Case's existing single-task-to-single-PR link), `contractService`/`caseService`/`quotationService`/`companyService` (belongsTo, confirmed live in the 2026-09-15 spec's §4 and again in this session's screenshots).

**Open item**: `caseService`'s raw FK column name (likely `caseServiceId` or `projectServiceId` — this project has a recurring gotcha where a `belongsTo` association's display/API name differs from its actual `foreignKey` column, already hit once with `linkedPaymentRequestId` → real column `paymentRequestId`). Confirm the real column name via the `fields` metadata table before writing the By Service trigger (§5) — the same verification step the 2026-09-15 spec already had to do for `tasks.linkedPaymentRequestId`.

## 5. Automation logic

### By Case — rewritten from JSON-parsing to row-based

| Trigger (current, JSON-based) | Replacement (row-based) |
|---|---|
| `by_case_create_scheduled_payment_requests()` — `AFTER INSERT ON contracts`, loops `jsonb_array_elements(paymentSchedule->'installments')` | `AFTER INSERT ON "contractPaymentSchedule"` — one row insert = one PR created directly, no JSON parsing. Sets `contractPaymentScheduleId = NEW.id`, `installmentNo = NEW."installmentNo"`, `sourceSnapshot = jsonb_build_object('label', NEW.label, 'percentage', NEW.percentage, 'amount', NEW.amount)`. |
| `by_case_task_done_activates_payment_request()` | Unchanged — still keyed off `tasks."paymentRequestId"`, nothing here depends on where the PR came from. |
| `by_case_case_done_activates_payment_request()` | Unchanged. |
| `by_case_due_date_activates_payment_request()` | Unchanged — already generic over any `paymentRequests` row regardless of contract type, reused as-is by By Service below. |

Consequence for `ContractCreateForm.js`: building a schedule becomes inserting `contractPaymentSchedule` rows (one API call per installment, or a bulk create) instead of assembling a `paymentSchedule` JSON blob. `ContractDetailView.js` / `ContractPaymentScheduleDetailBlock.js` switch from parsing `contract.paymentSchedule.installments` to querying `contractPaymentSchedule` filtered by `contractId` (with `appends: ["paymentRequests"]` to get each installment's generated PR in one call).

### By Service — new trigger, PR creation instead of activation

New function `by_service_task_group_done_creates_payment_request()`:

- **Fires**: `AFTER UPDATE OF status ON tasks`.
- **Guard**: `NEW."isPaymentTrigger" = true AND NEW.status = 'done' AND NEW."<caseServiceRawColumn>" IS NOT NULL` (exact column name from §4's open item).
- **Check**: among sibling tasks sharing the same case-service link (`WHERE "<caseServiceRawColumn>" = NEW."<caseServiceRawColumn>" AND "isPaymentTrigger" = true`), are they now **all** `status = 'done'`? (AND logic, per the confirmed business rule — not ANY-one-of-them.)
- **Idempotency guard**: skip if a `paymentRequests` row already exists with `"projectServices" = NEW."<caseServiceRawColumn>"` (a service's task group can only produce one PR, ever — re-marking a task done after being reopened must not create a second one).
- **If both conditions hold**: look up the `projectServices` row (for `totalAmount`, `contractServiceId`) and its parent `contracts` row (via `projectServices` → `projects` → `contractId`, or directly if `projectServices.contractServiceId` → `contractServices.contractId` gives a shorter path — confirm which join is available), then `INSERT INTO "paymentRequests"` with `status = 'pending'`, `conditionMet = true` (the task condition already happened by definition), `triggerType = 'on_task_done'`, `projectServices = <the service row id>`, `contractServices = <its contractServiceId>`, `requestedAmount = projectServices.totalAmount`, `sourceSnapshot = jsonb_build_object('serviceName', ..., 'totalAmount', ...)`, `dueDate = NULL` — stays `pending` until a human sets a due date, at which point the existing, unchanged `by_case_due_date_activates_payment_request()` trigger activates it exactly like a By Case installment.

This mirrors the By Case pattern closely enough that the *activation half* (due-date trigger) is shared code — only the *creation half* differs (upfront-at-signing for By Case vs. task-group-completion for By Service).

## 6. Schema confirmed (via `JsField/DiagnoseUnifiedPaymentSchemaFields.js`, run 2026-09-17)

1. **Table name**: `contractPaymentSchedules` (plural, tableName same as collection name).
2. **`tasks` raw FK columns**: `caseService` → `projectServiceId`; `contractService` → `contractServiceId`; `linkedPaymentRequestId` → `paymentRequestId` (already known); `isPaymentTrigger` confirmed present, no FK.
3. **`contractPaymentSchedules.triggerType`** option list confirmed identical to `paymentRequests.triggerType`: `on_signed` / `on_task_done` / `on_case_done`.
4. **`sourceSnapshot`** (json, on `paymentRequests`) has no description set in the field metadata — its intended shape is not otherwise documented. This spec proceeds with a minimal proposed shape (§5: `{label/serviceName, percentage, amount/totalAmount}` depending on contract type) as a reasonable audit-trail default; adjust later if the user had something more specific in mind.
5. **Join path `projectServices` → `contracts`**: `projectServices` has no direct `contractId` column. Path is `projectServices.projectId → projects.id → projects.contractId → contracts.id`. Its originating `contractServices` row (nullable — an ad-hoc case service added directly on the case has none) is found via the reverse link `contractServices.projectServiceId = projectServices.id`.

Full field dumps for `contractPaymentSchedules`, `paymentRequests`, `tasks`, `projectServices`, `contractServices` are preserved in this session's diagnostic output — see `JsField/DiagnoseUnifiedPaymentSchemaFields.js` for the script that produced them.

**Revision (same day)**: `contractPaymentSchedules` initially had no `dueDate` column, which would have meant every new request always starting `pending` with no due date — even an `on_signed` installment filled in at signing. The user added a `dueDate` column to `contractPaymentSchedules` to restore the old immediate-activation behavior. To avoid the two-places-to-update risk §4 originally warned about, this is treated as a **one-way seed value, not a synced field**: `by_case_schedule_row_creates_payment_request()` copies `NEW."dueDate"` onto the new `paymentRequests` row at creation time only (also into `sourceSnapshot` and `paymentRequestItems.plannedPaymentDate`, mirroring the old JSON-based flow). After that INSERT, only `paymentRequests.dueDate` matters — editing it later never writes back to the schedule row, and editing the schedule row's `dueDate` after its request already exists has no effect (the trigger only fires on `INSERT`).

## 6b. Revision (2026-09-21) — catch-up for tasks done before a contract exists

A real sequence in practice: a case starts work before its contract is signed/linked, so a task can already be marked `done` (with `isPaymentTrigger = true`) while `projects.contractId` is still null. The tasks-status trigger's guard (`v_project."contractId" IS NULL THEN RETURN`) correctly no-ops in that moment — but nothing ever re-checked that task once a contract was linked afterward, since the tasks trigger only runs at the instant a task's own status changes.

Fixed by extracting the "is this service's task group fully done, and does it not already have a Payment Request" check out of `by_service_task_group_done_creates_payment_request()` into a shared function, `by_service_check_and_create_payment_request(p_project_service_id)`, callable from two triggers:
- `trg_by_service_task_group_done_creates_payment_request` (tasks AFTER UPDATE OF status) — unchanged trigger point, now a thin guard that calls the shared function.
- `trg_by_service_contract_linked_catches_up_done_tasks` (**new**, projects AFTER UPDATE OF `"contractId"`) — fires whenever a case's contract link is set/changed, loops every distinct `projectServiceId` among that case's `isPaymentTrigger` tasks, and re-runs the same check for each. Safe to call for a service that isn't actually ready — the shared function re-verifies the group and idempotency itself.

No schema change — this is SQL-only, in `pgsql/unified_contract_payment_schedule.sql`.

## 6c. Revision (2026-09-21) — priority, default due date, auto-generated request note

Both PR-creation triggers (`by_case_schedule_row_creates_payment_request`, `by_service_check_and_create_payment_request`) now also set:
- `priority = 'high'` (confirmed live enum: `low`/`normal`/`high`/`urgent`).
- `dueDate`: By Case respects an explicit due date set on the schedule row (`contractPaymentSchedules.dueDate`) if the lawyer set one; otherwise defaults to `now() + 7 days`. By Service has no input due date at all (it's purely computed), so it's always `now() + 7 days`. Since a due date is now always present, By Service's request starts directly at `status = 'active'` (conditionMet is already guaranteed true by its own guards) instead of `'pending'`.
- `requestNote`: auto-generated — By Case: `Yêu cầu thanh toán tự động của đợt "{label}" từ ngày tạo {date}`; By Service: `Yêu cầu thanh toán tự động của các task: {comma-separated trigger task titles} từ ngày tạo {date}`.

Applied to both triggers identically (by user's explicit choice) so the two mechanisms don't diverge in behavior for a lawyer reviewing requests from either source.

## 6d. Revision (2026-09-21) — isPaymentTrigger checkbox no longer gated by contractType

Removed the `contractType === "byService"` gate on the `isPaymentTrigger` checkbox in all 3 places (`CaseCreateForm.js`'s Sample Tasks table, `TaskDetailView.js`, `TaskManagement.js`) — at the user's explicit request, it's now visible/configurable on every task regardless of the case's contract type, or whether the case has a contract linked at all. Reasoning: the SQL side already no-ops safely without a By Service contract (the `contractId IS NULL` guard in `by_service_check_and_create_payment_request`), so hiding the UI added friction (a lawyer configuring a case ahead of its contract being signed had nowhere to mark trigger tasks) without adding real safety. `TaskManagement.js`'s now-unused `contractType` fetch/state/prop-threading was removed entirely as dead code.

The By Case "Đợt thanh toán sẽ kích hoạt khi Done" selector in `TaskDetailView.js` keeps its own `contractType === "byCase"` gate unchanged — that mechanism genuinely requires a By Case contract's installment list to exist, so ungating it wouldn't make sense the same way.

## 6e. Revision (2026-09-21) — By Case gap: task linked to a PR after already being done

Investigated whether "Case created first, Contract linked later" causes the same gap for By Case as it originally did for By Service, and confirmed a real one: By Case's task-activation trigger only fires on `tasks AFTER UPDATE OF status`. The "Đợt thanh toán sẽ kích hoạt khi Done" selector (`TaskDetailView.js`) that lets a lawyer pick which installment a task activates only offers options once the case's contract is linked (it queries `paymentRequests` by `contractId`). If a task is marked done *before* the contract exists, there's nothing to select yet — and linking it to an installment *afterward* only changes `paymentRequestId`, not `status`, so the existing trigger never re-fires. That installment would stay stuck `pending` forever, with no automatic path to `active` even after the lawyer does the linking correctly.

Retainer was checked too and confirmed to have **no equivalent gap** — its billing (`JsField/Workflow/CreateContractBillingPlansWorkflow.js`, a schedule-type Workflow on `contractBillingPlans.nextBillingDate`) never references `projects`/`tasks` at all; it fires purely on calendar dates regardless of whether any case exists.

Fixed by extracting the "activate a pending PR if it's still pending" logic out of `by_case_task_done_activates_payment_request()` into a shared function, `by_case_activate_payment_request_if_ready(p_payment_request_id)`, and adding a new mirror trigger, `by_case_task_linked_activates_payment_request()` (`tasks AFTER UPDATE OF "paymentRequestId"`), that calls the same shared function whenever a task already at `status = 'done'` gets linked to a PR. Both triggers now converge on one shared activation check, covering both orderings symmetrically — the same pattern already used for By Service's own catch-up trigger. No schema change; SQL only, in `pgsql/by_case_payment_request_automation.sql`.

## 6f. Revision (2026-09-21) — unify the two trigger UI controls in TaskDetailView.js

Showing both controls side by side (By Case's installment Select and By Service's `isPaymentTrigger` checkbox) on every task, regardless of type, was confusing — whichever one didn't match the case's actual contract type had zero effect but still occupied UI space. Merged into one checkbox, "Task này là điều kiện thanh toán", whose `onChange` branches on `caseInfo.contractType`:
- **By Service**: writes `isPaymentTrigger` directly, unchanged from before.
- **By Case**: the checkbox itself never writes `isPaymentTrigger` (meaningless there) — ticking it only reveals the installment Select below (a local-only reveal flag, `byCaseSelectorOpen`, reset per task via a `useEffect` keyed on `item?.id`); nothing is written until an installment is actually picked. Unticking an already-linked task clears `linkedPaymentRequestId` immediately (confirmed explicitly with the user — unticking means removing the link, not just hiding the selector).

Also fixed, in the same file: `linkablePaymentRequests` was fetched with `status: 'pending'` in its filter, so a task's own already-linked installment dropped out of the Select's `options` the moment that request activated — the Select then had no matching option to resolve a label from and fell back to rendering the raw numeric id instead of "Đợt N - ...". Removed the status filter (selecting an already-active request again is a harmless no-op — `by_case_activate_payment_request_if_ready()` only acts on a still-`'pending'` request).

## 6g. Revision (2026-09-21) — mirror the unified control into TaskManagement.js's table

`TaskManagement.js`'s "Trigger Payment" column was still a plain `isPaymentTrigger` checkbox on every row regardless of contract type — a UI/UX mismatch against `TaskDetailView.js`'s now contract-type-aware control (§6f): a By Case task's checkbox there did nothing (By Case automation never reads `isPaymentTrigger`), and there was no way to pick an installment without leaving the table for Task Detail.

Fixed by giving the "Trigger Payment" column the same branch `TaskDetailView.js` uses, at the column level rather than per-row (`TriggerCell`, renamed from `TriggerCheckbox`): one case has exactly one contract, so `contractType` is the same for every row in the table, letting the whole column pick one rendering mode instead of branching per task.
- **By Case**: a compact `Select` over `linkablePaymentRequests`, writing `linkedPaymentRequestId` directly — no progressive-disclosure reveal step (unlike `TaskDetailView.js`'s checkbox-then-select), since the table already shows one row per task.
- **Anything else** (By Service / Retainer / no contract yet): the `isPaymentTrigger` checkbox, unchanged.

`ProjectTasksTab`'s `reload()` gained the same `projects:get → contracts:list` / `paymentRequests:list` (no `status` filter, per §6f) chain already proven in `TaskDetailView.js`, feeding new `contractType`/`linkablePaymentRequests` state threaded down `ListView → ServiceSection → TaskRow → TriggerCell`.

Also consolidated as part of this change: `handleToggleTrigger` (wrote only `isPaymentTrigger`) was replaced by a generalized `handleUpdateTaskField(id, field, value)`, so both write paths (`isPaymentTrigger` from the checkbox, `linkedPaymentRequestId` from the new Select) share one permission-check/optimistic-update/error-handling body instead of duplicating it per field.

## 6h. Revision (2026-09-21) — By Case: tag each installment with the service(s) it belongs to

Before this, a By Case contract with several services had one payment schedule computed off the whole contract total, with no link at all to which service an installment was actually "for" — every By Case task in the case could pick any installment regardless of its own service.

Added a new optional, multi-select field on each Payment Schedule row in `ContractCreateForm.js` — "Service" (`PaymentScheduleServiceSelect`, options from the services already selected above via `paymentScheduleServiceOptions`, keyed by `lineKey(line)` for a catalog line or `row.id` for a manual one). Left empty (the default, and the state of every installment created before this revision) means "no particular service" — visible to every task, same as before this field existed.

**Data model**: 2 new junction collections, created via Admin UI — mirrors this codebase's existing `serviceCombos`/`serviceComboItems` pattern (an explicit junction collection with plain integer FK fields) rather than a JSON array field or NocoBase's own auto-generated many-to-many through table, so both the raw table/column names are exactly what's declared (no diagnostic-script guessing needed before writing the trigger) and the CRUD is the same plain `<collection>:create` calls used everywhere else in this codebase:
- `contractPaymentScheduleServices` — `contractPaymentScheduleId` (bigInt), `contractServiceId` (bigInt). Written at contract-creation time.
- `paymentRequestServices` — `paymentRequestId` (bigInt), `contractServiceId` (bigInt). Populated by the updated `by_case_schedule_row_creates_payment_request()` (`pgsql/unified_contract_payment_schedule.sql`), copying each matching `contractPaymentScheduleServices` row onto the newly created Payment Request.

Both collections also carry a `belongsTo` field on each side (e.g. `contractPaymentSchedule`/`contractService`) for Admin UI relation-graph visibility — unused by the JS code below, which reads/writes the 2 plain FK columns directly.

**Resolving local keys to real ids**: the schedule rows are edited (and their local `serviceKeys` chosen) before the contract or its services exist in the DB. `ContractCreateForm.js`'s submit handler was reordered — `contractPaymentSchedules:create` now runs AFTER both service-creation loops (catalog `serviceLinesForSubmit` and manual `manualServiceRowsForSubmit`), which populate a new `contractServiceKeyMap` (`lineKey(line)` or `row.id` → real `contractServiceId`) as each service line is created. Each installment's `serviceKeys` is resolved through this map, then — once the schedule row itself is created and its own id is known — one `contractPaymentScheduleServices:create` call per resolved service id tags it.

**Task-side filtering** (`TaskDetailView.js` and `TaskManagement.js`, both By Case installment pickers): 2 new fetches. First, a reverse-link, `contractServices:list` (`id,projectServiceId`) for the case's contract, builds a `projectServiceId → contractServiceId` map (same join path as the SQL trigger's own header comment: `contractServices.projectServiceId = projectServices.id`). Second, once `linkablePaymentRequests` resolves, `paymentRequestServices:list` filtered by `paymentRequestId: {$in: [...those PR ids]}` builds a `paymentRequestId → [contractServiceId, ...]` map. An installment is offered to a task when either it has no entry in that second map (applies to everyone), or the task's own `projectServiceId` resolves — via the first map — to a `contractServiceId` present in the second map's entry for that PR. The task's *already-linked* installment is always kept in the options regardless of this filter (same reasoning as §6f's raw-ID fix — a task's service can change after linking, and the Select must still resolve a label for its current value).

## 6i. Revision (2026-09-21) — payment mode UI split + retainer "week" unit

**UI-only mode grouping**: `ContractCreateForm.js`'s single "Contract type" Select (byCase/byService/retainer) is now presented as 2 steps — "Payment mode" (Non-recurring / Recurring (Retainer)), then, only when "Non-recurring" is chosen, "Contract type" (By Case / By Service). `contracts.contractType` in the DB is untouched — still exactly the same 3 values — this is purely `PAYMENT_MODE_OPTIONS`/`NON_PERIODIC_CONTRACT_TYPES` reorganizing the same `handleContractTypeChange` handler into 2 Selects instead of 1. (Both Selects' text was originally shipped in Vietnamese — a mismatch with the rest of this English-language form — and translated to English the same day, §6j.)

**Gate audit** (the "constrain option values per type" half of the same request): found and fixed one real leak — `showGenericPaymentDates` (`!isRetainer && !isMultiplePayments`) showed a "First payment" date field for By Service contracts, even though By Service has no singular first-payment concept (its Payment Requests are created per-service, driven by `tasks.isPaymentTrigger`, never by this date). Split into `showFirstPaymentDate` (`isByCase && !isMultiplePayments`) and `showContractEndDate` (`!isRetainer`, kept broad — a contract's validity end date is a reasonable field for both By Case and By Service).

**Retainer "week" unit**: added `{ value: "week", label: "tuần" }` to `RETAINER_REPEAT_ANCHORS`, a `week` branch to `calcRetainerNextPaymentDate` (`addDays(date, duration * 7)`), and `"week"` to the submit-time repeat-unit whitelist. `retainerDurationSuffix` already had a `week` case from before this revision (unused until now). No backend change needed: `CreateContractBillingPlansWorkflow.js`'s `dateCalculation` node passes `retainerUnit` straight through to a `dayjs().add(number, unit)` call (confirmed by reading `plugin-workflow-date-calculation`'s server code and NocoBase's own `dayjs` unit test suite in the reference monorepo) — dayjs accepts `'week'` exactly like the `'day'/'month'/'year'` values already in use, no unit whitelist blocks it.

**Leap-year handling for the "year" unit** (also asked about): already correct on both sides, no code change needed. Frontend: `addMonthsClamped(date, duration * 12)` adds whole months and clamps the day to the target month's actual length — Feb 29 + 12 months lands on Feb 28 the following (non-leap) year. Backend: `dayjs().add(1, 'year')` has the identical clamping behavior natively. Both sides already agreed before this revision; this was a verification, not a fix.

## 6j. Revision (2026-09-21) — remove the per-installment Trigger picker; restrict Billing cycle; English labels

**`PaymentCreateBlock.js` — consolidation, not new fixes**: §6u had added a *second*, DB-sourced "Outstanding" line alongside the pre-existing client-computed `contractRemainingAmount`, so the non-installment branch briefly showed the same number twice (grid's "Remaining" from the client calc, top bar's "Outstanding" from the DB column) — harmless but not "chuẩn" (a single standard). Fixed by introducing one `contractOutstandingAmount` (DB `outStandingAmount` preferred, `contractRemainingAmount` as the only fallback for pre-trigger contracts) and routing every consumer through it: the "Remaining" `ContractSummaryItem`, `handleAmountChange`'s payment-status derivation, and `validate()`'s overpayment/already-fully-paid checks (previously all read the client-only `contractRemainingAmount` directly). The top bar's "Outstanding: ..." text is now shown only in the installment-`Table` branch (the one place with no other contract-level total on screen); the non-installment grid branch relies on its own "Remaining" box, now backed by the same authoritative source — no more duplicate number on one screen.

## 6w. Revision (2026-09-22) — when a contract has explicit installments, outstanding must be summed from them, not read off the contract-level DB column

User pushed back on §6v/§6u's "DB `outStandingAmount` is the single source of truth" framing: for a contract that already has concrete installments (đợt thanh toán) — e.g. 3 installments with 3 Payment Requests already raised against them — the correct "nghiệp vụ finance mới" (new finance business rule) is to compute the outstanding amount **from those installments**, not from a contract-level total. Correct concern: `contracts.outStandingAmount` is `contract_resolved_total(id) − Σ payments`, computed against the *whole-contract* resolved total — mathematically equal to summing installment remainders only if the installments perfectly partition that total and every payment is correctly attributed to the right installment. If those ever drift (rounding, a contract total edited after installments were set, a payment posted against the wrong installment), the single DB number and the installment table shown right below it on screen could show two different truths — exactly the "not chuẩn" failure mode being fixed.

**Fix, in both `PaymentCreateBlock.js` and `PaymentContractDetailBlock.js`**: added `installmentBasedOutstanding` — when the contract has an explicit installment schedule (`isContractInstallmentPayment` / `isInstallmentContract`), it's `Σ installmentRemainingAmount(row)` over the exact rows rendered in the on-screen table (`contractInstallments`/`installmentRows`), computed with the same per-row helper the table itself uses for its "Remaining" column — so the top-line number and the table can never disagree, by construction. Precedence, most-preferred first: (1) installment-based sum, when installments exist; (2) `contracts.outStandingAmount` (DB), when there's no installment breakdown to sum (By Case single payment, By Service, Retainer); (3) client total-minus-payments recompute, only for pre-trigger contracts missing the DB column. Both files' `outstandingAmount`/`contractOutstandingAmount` now resolve through this 3-tier chain instead of going straight to the DB column.

**Not changed**: per-installment validation (`selectedRemainingAmount`, "Received amount cannot exceed installment remaining amount") was already correctly scoped to the single selected installment before this revision — untouched. `PaymentContractDetailBlock.js`'s `coveragePercent` automatically inherits the more accurate figure since it already derives from `outstandingAmount`.

## 6x. Revision (2026-09-22) — opening "Create Payment" from a Payment Request's own detail page; root-cause id-space mismatch found and fixed for that flow

User asked what happens when a user opens a Payment Request's own detail page and wants to create a Payment/Invoice for it. Investigating this surfaced a real, previously-undiscovered bug, confirmed by reading `ContractCreateForm.js`, `unified_contract_payment_schedule.sql`, and `CreateContractBillingPlansWorkflow.js` together:

**Root cause — two disconnected id spaces for "which installment":**
- `contracts.paymentSchedule` (JSON field) — each installment row's `id` is a client-generated temp string, `"payment-" + Date.now() + "-" + random()` (`ContractCreateForm.js`, `newPaymentScheduleRow`). This is what `PaymentCreateBlock.js`/`PaymentContractDetailBlock.js`'s `normalizeSchedule()` reads to build the on-screen installment Table (`contractInstallments`/`installmentRows`).
- `contractPaymentSchedules` (real DB collection) — a separate, server-generated bigint id, created in a *second, independent* API call right after the contract itself (`ContractCreateForm.js` line ~12140, `contractPaymentSchedules:create`). Nothing ever writes this real id back into the JSON blob's `id` field, so the two never reconcile.
- `paymentRequestItems.scheduleItemId` (set by the SQL trigger, `by_case_schedule_row_creates_payment_request()`) stores the **real** `contractPaymentSchedules.id`, not the JSON temp string.

Consequence: `PaymentCreateBlock.js`'s old `loadPaymentRequestContext()` read the real id from `paymentRequestItems.scheduleItemId`, then tried to find a matching row in `contractInstallments` (JSON-temp-id-keyed) — this **can never match** for any contract using the current architecture. Effect: the Table never pre-highlighted the right row, and — more seriously — `validate()`'s `isContractInstallmentPayment && !selectedInstallment` check could **block submission entirely** for a By Case Payment opened from a perfectly valid Payment Request. Separately, **Retainer's Payment Requests never get a `paymentRequestItems` row at all** (`CreateContractBillingPlansWorkflow.js`'s "create" node only inserts into `paymentRequests`) — so the old `seedPaymentRequestItemId`-only auto-load `useEffect` could never fire for Retainer in the first place.

**Fix, scoped to the "open from an existing Payment Request" flow** (confirmed with user: "Chuyển sang dùng paymentRequests/paymentRequestItems làm nguồn thật", over a narrower Retainer-only patch):
- New `activePaymentRequest` state replaces reliance on `contractInstallments`/`selectedInstallment` matching for this flow entirely. It holds the one already-known `paymentRequests` row's own `requestedAmount`, `paidAmount` (computed by filtering `contractPayments` on `payment.paymentRequestId === request.id` — an id space every payment already correctly carries, sidestepping the JSON/DB mismatch completely), `remainingAmount`, and `scheduleItemId` (taken from `paymentRequests.contractPaymentScheduleId` — the REAL id, present for By Case, null for By Service/Retainer).
- `loadPaymentRequestContext(requestItemId)` (item-based, By Case/By Service) and new `loadPaymentRequestContextByRequestId(requestId)` (request-only, the only path that works for Retainer) both funnel through one shared `finishLoadingPaymentRequest(request, item)`.
- The auto-load `useEffect` now tries `seedPaymentRequestItemId` first, then falls back to `seedPaymentRequestId` alone — so opening this block from a Payment Request's own detail page (which naturally only has the request's own id, not an item id) now works for all 3 contract types.
- `handleAmountChange`, `validate()`, and `buildPaymentPayload()` all check `activePaymentRequest` **first**, ahead of the old table/lump-sum branches — using `activePaymentRequest.remainingAmount` (re-verified against freshly-refetched payments at submit time, same anti-race pattern as the pre-existing installment branch) instead of any JSON-schedule-derived number. New `basePaymentRequestSourceKey`/`actualPaymentRequestSourceKey` dedupe keys mirror the existing `baseScheduleSourceKey`/`actualScheduleSourceKey` pattern (allows a second, later payment against the same request once the first has an actual amount/date/method filled in).
- Render: when `activePaymentRequest` is set, the installment Table/contract-total grid is replaced by a small 4-box summary (This request / Requested / Already received / Remaining on this request) — there is no ambiguity to resolve via a picker since the user already opened one specific, known Payment Request.
- `installmentBasedOutstanding` (§6w) is now gated on `!activePaymentRequest` — it must not fire when a request is active, since payments created through this new path carry the *real* `scheduleItemId`, which the JSON-blob-keyed sum can't see; it would silently ignore them and overstate the contract-wide "Outstanding" figure. `contracts.outStandingAmount` (DB) is used instead in that case, as originally intended by §6v/§6w's fallback chain.

**Known residual gap, not fixed in this pass**: the manual "By contract" Table (picking an installment without going through a specific Payment Request) still reads `contract.paymentSchedule` JSON and is unaffected by this fix — same for `PaymentContractDetailBlock.js`'s own `installmentRows`/"Fully paid installments" stats, which are read-only and were not touched. Both still key `summarizePaymentsByInstallment`/`buildInstallmentRows` off `payment.scheduleItemId`, so **any payment now created via the new `activePaymentRequest` path (real id) will not be recognized as "paid" by these two JSON-blob-based per-row lookups** — going forward, as most By Case payments are created via the Payment-Request-driven flow (the common path), the Table's own per-row "Received"/"Remaining"/"Status" columns and `PaymentContractDetailBlock.js`'s installment-progress stats will increasingly under-count. The durable fix is to retire `contract.paymentSchedule` JSON as an installment identity source everywhere and switch both Tables to read `contractPaymentSchedules`/`paymentRequests` directly (mirroring `TaskManagement.js`'s already-correct pattern) — flagged for the user to prioritize as a follow-up, not done here since it's a larger change than what was asked this round.

## 6y. Revision (2026-09-22) — `PaymentCreateBlock.js`'s manual "By contract" picker retired the `contract.paymentSchedule` JSON entirely; By Service now gets a picker for the first time

User closed the §6x residual gap: asked for the manual "By contract" flow (picking a contract without opening from one specific Payment Request) to list By Case's installments and By Service's per-service requests from real data, matching the design already proven for the direct-open flow. Confirmed via brainstorming: By Case and By Service share one picker component (both are "pick 1 of N `paymentRequests` rows for this contract", differing only in label — and `paymentRequests.title` is already set correctly per type by the SQL triggers, e.g. "Đợt N - ..." vs "Dịch vụ X - ...", so no per-type branching was even needed); a contract with zero real `paymentRequests` (legacy, pre-migration) falls back to the existing whole-contract-total grid rather than resurrecting any JSON matching.

**New state**: `contractPaymentRequests` — the contract's own `paymentRequests` rows (`id, title, requestedAmount, status, dueDate, contractPaymentScheduleId`), fetched alongside `contract`/`payments` in `loadContractContext`. `showPaymentRequestPicker` gates on contract type (`byCase`/`byService` only — Retainer's Payment Requests are periodic billing cycles, not a static list, and keeps using the grid) and `contractPaymentRequests.length > 0`.

This means validate()/`buildPaymentPayload()`/the summary-card render needed **zero additional branching** — they already treat "opened from a specific Payment Request" and "picked one from this new Table" identically, by design.

**2026-09-23 follow-up — multi-select considered and declined; checkbox toggle kept as the "change" mechanism**: user asked to allow ticking several requests at once (checkbox instead of radio) to record one combined payment. ## 6z. Bug fix (2026-09-23) — `payments."paymentRequestId"` was never a real column; every §6x/§6y "which request is this paid against" link was silently discarded

User reported: created a Payment (5,000,000 VND, status "Partial") against contract CT15092026's Đợt 1 via the new picker, then reopened "Create Payment" for the same contract — the picker table still showed Đợt 1 as Received: 0 / Remaining: full amount, and "Contract outstanding" still showed the full un-paid total.

**Root-caused with `JsField/DiagnosePaymentRequestLinkage.js`** (read-only, dumps a payment row's raw fields with no `fields` restriction so nothing is hidden): `contracts.outStandingAmount` HAD correctly dropped by exactly 5,000,000 (29,700,000 → 24,700,000) — proving the SQL trigger side (`contract_recompute_outstanding`, contract-total-based) was fine. But the payment record itself had **no `paymentRequestId` key at all** — not even as `null` (every other unset field, e.g. `invoiceId`, `lawyerId`, `currencyId`, showed up as an explicit `null`; a genuinely undefined field is omitted from the response entirely). `buildCommonPaymentPayload()` (§6x onward) had always written `payload.paymentRequestId`/`payload.paymentRequest` on create, but **the `payments` collection never had these fields registered** — Nocobase silently drops unknown keys on `:create` instead of erroring, so every payment ever created through the Payment-Request-driven flow saved its amount/date/method correctly but the link back to which `paymentRequests` row it was for was never persisted. `paymentRequestPaidAmount()`'s `extractId(p?.paymentRequestId) === extractId(request?.id)` was therefore always comparing `undefined`, silently returning `false` for every row — not a logic bug in the matching code itself, a schema gap underneath it.

**What did survive**, confirmed in the same raw dump: `scheduleItemId: "388016528556033"` — correctly matches Đợt 1's `contractPaymentScheduleId` (this write path was fine, §6x); and `sourceKey: "paymentRequest:1790044698085496"` — `basePaymentRequestSourceKey()`'s own dedup key, which happens to encode the exact `paymentRequests.id` as its 2nd `:`-delimited segment.

**Fix, two parts**:
1. `JsField/RegisterPaymentRequestLinkFields.js` — registers `payments.paymentRequest` (belongsTo → `paymentRequests`, FK column `paymentRequestId`) and `payments.paymentRequestItem` (belongsTo → `paymentRequestItems`, FK column `paymentRequestItemId`) as proper Nocobase relations, same pattern as the already-proven `RegisterPaymentRequestAssignedLawyerField.js`. Nocobase's `fields:create` creates the underlying FK column itself. Idempotent (skips if already registered).
2. `pgsql/backfill_payment_request_id_from_source_key.sql` — one-time backfill for payments created *before* the field existed: `UPDATE payments SET "paymentRequestId" = split_part("sourceKey", ':', 2)::bigint WHERE "paymentRequestId" IS NULL AND "sourceKey" LIKE 'paymentRequest:%'`. Scoped only to payments whose `sourceKey` has that prefix (i.e. created via the §6x/§6y `activePaymentRequest` path) — payments from other modes/the old JSON-Table flow have no reliable id to recover (same id-space mismatch as §6x) and are left untouched. Must run *after* step 1 (column has to exist first).

**No `PaymentCreateBlock.js`/`PaymentContractDetailBlock.js` code changes needed** — the read-side matching logic was already correct; it was reading a column that silently never existed. Deployment order matters: run the field-registration script, then the SQL backfill, then existing payments like this 5tr one will correctly show up as this Đợt's "Received" amount without any further action.

**Verified fixed (2026-09-23)**: user ran both scripts, then re-ran `JsField/DiagnosePaymentRequestLinkage.js` — payment #80's `paymentRequestId` now reads `1790044698085496`, exactly matching Đợt 1's `paymentRequests.id`. Confirmed via raw data before declaring done, not just "script ran with no error".

**Retired as dead code** (no longer had any caller after this change): `normalizeSchedule`, `contractScheduleMode`, `isInstallmentPaymentContract`, `summarizePaymentsByInstallment`, and the old JSON-driven `contractInstallments`/`selectedInstallment`/`selectedInstallmentId`/`handleInstallmentSelect`/`isContractInstallmentPayment`/`installmentPaidAmount`/`installmentRemainingAmount`/`isInstallmentFullyPaid`. `buildPaymentPayload()`'s contract-mode branch simplified from 3 cases (activePaymentRequest / JSON-installment / whole-contract) down to 2 (activePaymentRequest / whole-contract fallback), since the picker's own selection always produces an `activePaymentRequest` now. `contractOutstandingAmount`'s installment-sum tier (§6w) was renamed `requestBasedOutstanding` and now sums `contractPaymentRequests` (real ids) instead of the JSON blob.

**Still out of scope**: `PaymentContractDetailBlock.js` (read-only, historical view) still reads `contract.paymentSchedule` for its installment-progress stats — same §6x residual gap, not touched by this revision. `InvoiceGenerator.js` was not examined.
